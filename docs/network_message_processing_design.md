# 网络消息处理架构设计文档

> **作者视角**：10+ 年 IM 架构师、分布式系统设计专家、跨端 SDK 内核设计专家  
> **参考实践**：微信、Telegram、飞书、WhatsApp、Discord 核心架构  
> **设计目标**：生产级、可扩展、高性能、可维护

## 1. 架构概述

### 1.1 设计原则

基于顶级 IM 系统的架构实践，采用**分层处理 + 事件驱动 + 异步流水线**的设计模式：

1. **职责分离**：网络层只负责协议识别，协议层负责解析路由，应用层负责业务处理
2. **性能优先**：避免重复解析，批量处理，零拷贝优化
3. **可扩展性**：插件化设计，支持新的 payload 类型和业务扩展
4. **可观测性**：完整的日志、指标、追踪链路
5. **错误恢复**：优雅降级，向后兼容，自动重试
6. **状态一致性**：确保消息顺序、会话状态、同步游标的强一致性

### 1.2 分层架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                    应用层 (Application Layer)                        │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐             │
│  │ Message      │  │ Sync         │  │ Custom Data  │             │
│  │ Processor    │  │ Processor    │  │ Processor    │             │
│  │              │  │              │  │              │             │
│  │ - 消息入队    │  │ - 批量处理    │  │ - 类型分发    │             │
│  │ - 持久化      │  │ - 游标更新    │  │ - 扩展路由    │             │
│  │ - 会话更新    │  │ - 触发后续    │  │ - 事件发布    │             │
│  │ - 事件发布    │  │ - 状态同步    │  │              │             │
│  └──────────────┘  └──────────────┘  └──────────────┘             │
└─────────────────────────────────────────────────────────────────────┘
                            ▲
                            │ NetworkMessage (分类后的消息/数据)
                            │
┌─────────────────────────────────────────────────────────────────────┐
│                  协议层 (Protocol Layer)                              │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │              Message Router (无状态路由器)                    │   │
│  │  - 协议识别 (ServerPacket / MessageEnvelope / Message)       │   │
│  │  - 消息分类 (Message / Sync / Custom / ACK)                  │   │
│  │  - 路由分发 (根据类型分发到不同通道)                            │   │
│  │  - 协议降级 (向后兼容处理)                                      │   │
│  └──────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
                            ▲
                            │ Frame (原始网络帧)
                            │
┌─────────────────────────────────────────────────────────────────────┐
│                   网络层 (Network Layer)                              │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │         NetworkMessageListener::on_message                   │   │
│  │  - ACK 快速过滤 (由 send_frame_and_wait 处理)                 │   │
│  │  - MessageCommand 类型判断 (Type::Send = 0)                   │   │
│  │  - 快速转发到协议层 (不做解析)                                  │   │
│  └──────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.3 核心设计理念

**对标微信、Telegram、飞书的架构实践**：

1. **网络层极简**：只做帧级别的过滤和转发，不做任何业务判断
2. **协议层专业**：专门负责协议解析、分类、路由，无状态设计
3. **应用层业务**：按消息类型分发到专门处理器，支持批量处理和异步流水线
4. **事件驱动**：通过 EventBus 解耦 UI 层和业务层
5. **状态机管理**：通过 FSM 管理连接状态、同步状态，确保一致性

## 2. 五种消息类型的处理架构

### 2.1 收到消息的处理 (Message Delivery)

**架构设计思路**：

**完整流程**：
```
Frame (网络层)
  ↓
on_message (快速过滤 ACK，识别 MessageCommand)
  ↓
MessageRouter (协议识别，路由决策)
  ↓
NetworkMessage::Received(Frame) (转发原始 Frame)
  ↓
MessageQueue (去重、优先级排序)
  ↓
MessageQueueProcessor (批量处理，异步流水线)
  ↓
DefaultMessageHandler::handle_message
  ├─→ 1. 解析 MessageEnvelope → 提取 Message (延迟解析)
  ├─→ 2. 保存到 ReadStore (持久化，确保数据不丢失)
  ├─→ 3. 更新/创建会话 (通过 ConversationDomainService)
  │     ├─→ 更新最后一条消息
  │     ├─→ 更新未读数 (如果不是自己发送的)
  │     └─→ 更新 max_seq
  ├─→ 4. 发布事件到 EventStore (持久化事件)
  └─→ 5. 发布事件到 EventBus (实时通知 UI 层)
```

**架构要点**：

1. **异步流水线设计**
   - 网络层 → 队列 → 处理器 → 存储 → 事件，各环节异步解耦
   - 使用 Channel 传递消息，避免阻塞
   - 支持背压，队列满时自动丢弃低优先级消息

2. **批量处理优化**
   - MessageEnvelope 可能包含多条消息，批量处理而非逐条
   - 批量写入 ReadStore，减少 I/O 次数
   - 批量更新会话，减少数据库操作

3. **去重机制**
   - MessageQueue 内置去重，基于 message_id
   - 去重窗口：5 分钟（可配置）
   - 支持幂等处理，确保消息只处理一次

4. **事件驱动架构**
   - 处理完成后发布事件，UI 层通过 EventBus 订阅
   - 事件包含完整的消息数据，UI 层无需再次查询
   - 支持多个订阅者，解耦 UI 层和业务层

5. **错误隔离和恢复**
   - 单条消息处理失败不影响其他消息
   - 可重试的错误自动加入重试队列
   - 不可重试的错误记录日志，上报监控

**性能优化策略**：
- **优先级队列**：实时消息优先级 10，同步消息优先级 5
- **批量写入**：多条消息批量写入 ReadStore，减少 I/O
- **UPSERT 优化**：会话更新使用 UPSERT，避免先查询再更新
- **延迟解析**：只在需要时才解析 MessageEnvelope，避免不必要的解析

**参考实践**：
- **微信**：消息先入内存队列，异步持久化，批量更新会话，通过事件总线通知 UI
- **Telegram**：使用消息序列号去重，批量处理提高吞吐，事件驱动解耦 UI
- **飞书**：消息处理与 UI 渲染完全解耦，通过事件总线通信，支持多订阅者

### 2.2 同步消息的处理 (Sync Messages Response)

**架构设计思路**：

**完整流程**：
```
Frame (网络层)
  ↓
on_message (协议识别)
  ↓
MessageRouter (识别为 SyncMessagesResponse)
  ↓
NetworkMessage::SyncMessages(Response) (结构化数据)
  ↓
SyncHandler::handle_sync_messages_response
  ├─→ 1. 提取 MessageEnvelope (可能包含多条消息，批量提取)
  ├─→ 2. 批量解析消息 (避免逐条解析，提高性能)
  ├─→ 3. 批量入队 (使用批量接口，减少锁竞争)
  │     └─→ MessageQueue::enqueue_batch (批量入队)
  ├─→ 4. 等待批量处理完成 (确保所有消息已处理)
  ├─→ 5. 更新同步游标 (cursor / max_seq，原子更新)
  ├─→ 6. 判断 has_more，触发后续同步 (自动分页)
  │     └─→ SyncCoordinator::continue_sync (触发下一批)
  └─→ 7. 发布同步完成事件 (通知 UI 层同步进度)
```

**架构要点**：

1. **批量处理优先**
   - SyncMessagesResponse 通常包含多条消息（10-100 条），必须批量处理
   - 批量解析：一次性解析所有消息，避免逐条解析
   - 批量入队：使用批量接口，减少锁竞争
   - 批量写入：批量写入 ReadStore，减少 I/O 次数

2. **游标管理策略**
   - **更新时机**：所有消息处理完成后才更新游标，确保一致性
   - **原子更新**：游标更新使用事务，确保原子性
   - **断点续传**：支持从任意游标位置继续同步
   - **游标格式**：使用 cursor（字符串）和 max_seq（数字）双重游标

3. **分页处理机制**
   - has_more = true 时自动触发下一批同步
   - 使用 SyncCoordinator 管理同步流程
   - 支持并发同步（多个会话同时同步）
   - 支持同步限流，避免过载

4. **性能优化**
   - **批量写入**：多条消息批量写入 ReadStore
   - **批量更新会话**：批量更新会话，减少数据库操作
   - **并发处理**：多条消息并发处理，提高吞吐
   - **内存优化**：使用引用传递，避免不必要的克隆

5. **状态同步**
   - 同步完成后更新 FSM 状态
   - 通知 SyncCoordinator 同步进度
   - 支持同步暂停和恢复

**关键设计决策**：

**为什么单独处理？**
- 同步响应需要批量处理，与实时消息的处理路径不同
- 实时消息：单条处理，实时性优先
- 同步消息：批量处理，吞吐量优先

**游标更新时机？**
- 所有消息处理完成后才更新游标，确保一致性
- 如果部分消息处理失败，游标不更新，支持重试
- 使用事务确保游标更新的原子性

**错误处理策略？**
- 批量处理失败时，记录最后成功的位置
- 支持从失败位置重试，避免重复处理
- 部分失败时，更新游标到成功位置，失败的消息单独处理

**参考实践**：
- **微信**：同步消息批量处理，使用游标支持增量同步，支持断点续传
- **Telegram**：同步响应包含序列号范围，批量更新本地状态，支持并发同步
- **飞书**：同步消息与实时消息使用不同的处理队列，避免相互影响，支持同步限流

### 2.3 会话同步的处理 (Sync Conversations Response)

**架构设计思路**：

**完整流程**：
```
Frame (网络层)
  ↓
on_message (协议识别)
  ↓
MessageRouter (识别为 SyncConversationsResponse)
  ↓
NetworkMessage::SyncConversations(Response) (结构化数据)
  ↓
ConversationSyncHandler::handle_sync_conversations_response
  ├─→ 1. 解析 ConversationPatch 列表 (可能包含多个补丁)
  ├─→ 2. 补丁预处理 (按 conversation_id 分组，合并同一会话的补丁)
  ├─→ 3. 按 patch_type 分类处理：
  │     ├─→ LIGHT: 轻量更新 (只更新最后消息、未读数、时间戳)
  │     ├─→ SUMMARY: 全量更新 (更新完整会话信息)
  │     ├─→ REMOVED: 删除会话 (标记为已删除，不物理删除)
  │     ├─→ CREATED: 创建会话 (创建新会话，触发详情拉取)
  │     └─→ DETAIL_REQUIRED: 触发详情拉取 (异步拉取，不阻塞)
  ├─→ 4. 批量更新 ReadStore (使用批量 UPSERT)
  ├─→ 5. 更新会话游标 (server_conversation_cursor)
  ├─→ 6. 判断 has_more，触发后续同步 (自动分页)
  └─→ 7. 发布会话列表更新事件 (通知 UI 层刷新)
```

**架构要点**：

1. **补丁模式设计**
   - 使用增量补丁而非全量替换，减少数据传输和处理
   - 支持部分字段更新，只传输变更的字段
   - 补丁可以合并，同一会话的多个补丁合并处理

2. **分类处理策略**
   - **LIGHT**：轻量更新，只更新关键字段（最后消息、未读数）
   - **SUMMARY**：全量更新，更新完整会话信息
   - **REMOVED**：删除会话，标记为已删除（软删除）
   - **CREATED**：创建会话，触发详情拉取
   - **DETAIL_REQUIRED**：触发详情拉取，异步处理

3. **批量处理优化**
   - 多个补丁批量处理，减少数据库操作
   - 补丁预处理：按 conversation_id 分组，合并同一会话的补丁
   - 批量更新 ReadStore，使用批量 UPSERT

4. **游标管理**
   - 更新会话游标（server_conversation_cursor）
   - 支持增量同步，只同步变更的会话
   - 游标更新使用事务，确保原子性

5. **事件通知**
   - 发布会话列表更新事件，UI 层自动刷新
   - 事件包含变更的会话列表，UI 层可以增量更新
   - 支持多个订阅者，解耦 UI 层和业务层

**关键设计决策**：

**为什么单独处理？**
- 会话同步与消息同步的语义不同，需要不同的处理逻辑
- 会话同步使用补丁模式，消息同步使用批量消息
- 会话同步需要处理删除、创建等操作，消息同步不需要

**补丁合并策略？**
- 同一会话的多个补丁可以合并处理，减少更新次数
- 合并规则：LIGHT + SUMMARY → SUMMARY，REMOVED 优先
- 合并后的补丁一次性更新，提高性能

**详情延迟加载？**
- DETAIL_REQUIRED 时触发异步拉取，不阻塞同步流程
- 使用后台任务异步拉取详情，避免阻塞同步
- 拉取完成后更新会话，发布更新事件

**参考实践**：
- **微信**：会话列表使用增量同步，只传输变更的会话，支持补丁合并
- **Telegram**：会话更新使用补丁模式，支持部分字段更新，批量处理
- **飞书**：会话同步与消息同步分离，使用不同的同步策略，支持延迟加载

### 2.4 ACK 的处理 (Send Envelope Ack)

**架构设计思路**：

**完整流程**：
```
Frame (网络层)
  ↓
on_message (快速识别 ACK，Type::Ack = 1)
  ↓
直接返回 None (不进入应用层)
  ↓
send_frame_and_wait (flare-core 内部处理)
  ├─→ 1. 匹配等待的响应 (通过 message_id，O(1) 查找)
  ├─→ 2. 解析 SendEnvelopeAck (提取 status、error_code)
  ├─→ 3. 唤醒等待的 Future (通过 oneshot channel)
  ├─→ 4. 返回 ACK Frame 给调用者
  └─→ 5. 清理等待的响应 (从 pending_map 中移除)
```

**架构要点**：

1. **网络层快速过滤**
   - ACK 消息在网络层直接过滤，不进入应用层
   - 使用早期返回，减少不必要的处理
   - 保持网络层纯净，不包含业务逻辑

2. **自动匹配机制**
   - 由 `send_frame_and_wait` 自动匹配，无需手动处理
   - 使用 HashMap 存储等待的响应，O(1) 查找
   - 支持并发匹配，多个消息同时等待 ACK

3. **超时和重试机制**
   - 30 秒超时，超时后返回错误
   - ACK 失败时，消息进入重试队列
   - 支持指数退避，避免频繁重试

4. **状态更新**
   - ACK 成功后更新消息状态（Sent → Delivered）
   - 通过 MessageSender 更新消息状态
   - 发布消息状态变更事件

**关键设计决策**：

**为什么不在应用层处理？**
- ACK 是网络层的确认机制，与应用层业务无关
- 网络层处理更高效，减少不必要的路由开销
- 保持应用层纯净，不包含网络层逻辑

**为什么使用 send_frame_and_wait？**
- 自动处理 ACK 匹配，简化调用方逻辑
- 支持超时和重试，提高可靠性
- 统一的错误处理，便于排查问题

**错误处理策略？**
- ACK 失败时，消息进入重试队列
- 支持自动重试，使用指数退避
- 重试次数限制，避免无限重试

**参考实践**：
- **微信**：ACK 在网络层处理，应用层只关心业务结果，超时自动重试
- **Telegram**：使用消息序列号确认，ACK 自动匹配，支持并发匹配
- **飞书**：ACK 超时自动重试，支持指数退避，状态自动更新

### 2.5 自定义推送的处理 (Custom Push Data)

**架构设计思路**：

**完整流程**：
```
Frame (网络层)
  ↓
on_message (协议识别)
  ↓
MessageRouter (识别为 CustomPushData)
  ↓
NetworkMessage::CustomPushData { data_type, payload, metadata } (结构化数据)
  ↓
CustomDataHandler::handle_custom_push_data
  ├─→ 1. 根据 data_type 查找注册的处理器 (通过 ExtensionRegistry)
  ├─→ 2. 分发到对应的扩展处理器 (支持多个处理器)
  ├─→ 3. 扩展处理器处理业务逻辑 (异步处理)
  │     ├─→ 解析 payload (根据 data_type 使用不同的解析器)
  │     ├─→ 处理业务逻辑 (扩展自定义逻辑)
  │     └─→ 返回处理结果
  ├─→ 4. 错误处理 (单个扩展失败不影响其他)
  └─→ 5. 发布自定义事件到 EventBus (通知 UI 层)
```

**架构要点**：

1. **插件化设计**
   - 支持注册自定义的 data_type 处理器
   - 通过 ExtensionRegistry 管理扩展
   - 支持动态注册和卸载
   - 支持多个处理器处理同一 data_type

2. **类型分发机制**
   - 根据 data_type 路由到不同的扩展处理器
   - 支持通配符匹配（如 "order.*" 匹配所有订单相关）
   - 支持优先级，高优先级处理器先执行
   - 支持处理器链，多个处理器依次处理

3. **扩展机制集成**
   - 通过 Extension 机制注册处理器
   - 与 SDK 的扩展机制统一，便于管理
   - 支持扩展的初始化和销毁回调
   - 支持扩展的配置和状态管理

4. **事件发布设计**
   - 处理完成后发布自定义事件，UI 层可以订阅
   - 自定义事件使用独立的命名空间，避免冲突
   - 事件包含完整的处理结果，UI 层无需再次查询
   - 支持多个订阅者，解耦 UI 层和业务层

5. **错误隔离和恢复**
   - 单个扩展处理器失败不影响其他处理器
   - 错误记录日志，上报监控
   - 支持重试机制（如果扩展支持）
   - 支持降级处理（默认处理器）

**关键设计决策**：

**为什么使用插件化？**
- 自定义数据类型多样，无法在核心层硬编码
- 支持业务扩展，无需修改核心代码
- 支持第三方扩展，提高灵活性

**为什么通过 Extension？**
- 与 SDK 的扩展机制统一，便于管理
- 支持扩展的生命周期管理
- 支持扩展的配置和状态管理

**事件设计原则？**
- 自定义事件使用独立的命名空间（如 "custom.order.created"）

- 支持事件过滤，UI 层可以只订阅感兴趣的事件

**参考实践**：

- **Telegram**：自定义数据通过 Bot API 处理，支持第三方扩展，支持事件订阅

## 3. 网络层设计 (`listener.rs`)

### 3.1 职责边界

**网络层只负责**：
- ✅ ACK 消息快速过滤（Type::Ack = 1）
- ✅ MessageCommand 类型判断（Type::Send = 0）
- ✅ 快速转发到协议层

**网络层不负责**：
- ❌ 协议解析（避免重复解析，由协议层负责）
- ❌ 业务判断（保持网络层纯净，由应用层负责）
- ❌ 消息路由（由协议层负责）

### 3.2 实现思路

**on_message 简化设计**：
1. **快速 ACK 过滤**：检查 MessageCommand Type，如果是 ACK 直接返回 None
2. **类型判断**：只处理 Type::Send (0)，其他类型直接转发
3. **协议识别**：尝试解析 ServerPacket，失败则按向后兼容处理
4. **路由转发**：调用 MessageRouter 进行路由，转发到相应通道

**性能优化**：
- 使用早期返回，减少不必要的处理
- 避免在热路径中进行复杂解析
- 使用引用传递，减少内存拷贝

### 2.2 协议层职责 (`packet.rs` + `router.rs` 新增)

**职责**：协议解析和消息分类路由

#### 2.2.1 协议解析 (`packet.rs`)

```rust
parse_server_packet(payload) → PacketParseResult {
    - 解析 ServerPacket
    - 识别 payload 类型
    - 返回分类结果（不处理业务逻辑）
}
```

#### 2.2.2 消息路由 (`router.rs` 新增)

**新增模块**：`network/router.rs`

```rust
MessageRouter {
    // 根据 PacketParseResult 类型，分发到不同的通道
    route_packet(packet_result, frame) → NetworkMessage {
        match packet_result {
            Message(envelope) → NetworkMessage::Received(frame)
            SyncMessagesResponse(resp) → NetworkMessage::SyncMessages(resp)
            SyncConversationsResponse(resp) → NetworkMessage::SyncConversations(resp)
            CustomPushData(custom) → NetworkMessage::CustomPushData(custom)
            SendAck(ack) → 返回 None（已由 send_frame_and_wait 处理）
            ...
        }
    }
}
```

## 6. 消息类型扩展设计

### 6.1 NetworkMessage 枚举扩展

**设计思路**：根据不同的处理需求，定义不同的消息类型

**扩展后的枚举**：
- `Received(Frame)` - 实时消息（需要解析 MessageEnvelope）
- `SyncMessages(SyncMessagesResponse)` - 消息同步响应（批量处理）
- `SyncConversations(SyncConversationsResponse)` - 会话增量同步（补丁处理）
- `ConversationSyncAll(ConversationSyncAllResponse)` - 全量会话同步
- `ConversationDetail(GetConversationDetailResponse)` - 会话详情响应

- `Connected(String)` - 连接成功
- `Disconnected(String)` - 连接断开
- `Error(String)` - 连接错误

**设计原则**：
- 需要批量处理的类型，使用结构化数据
- 需要解析的类型，使用 Frame（延迟解析）
- 需要扩展的类型，使用结构化数据（便于分发）

## 8. 性能优化策略

### 8.1 避免重复解析

**问题分析**：
- 当前 `listener.rs` 和 `parser.rs` 都可能解析 ServerPacket
- 导致重复解析，浪费 CPU 和内存

**优化方案**：
1. **网络层**：只做协议识别，不解析 payload
2. **协议层**：解析 ServerPacket，识别 payload 类型
3. **应用层**：延迟解析 MessageEnvelope，只在需要时解析

**实现思路**：
- 使用 `Arc<Frame>` 共享 Frame，避免克隆
- 解析结果缓存（如果需要多次使用）
- 批量解析 MessageEnvelope 中的多条消息

### 8.2 批量处理优化

**同步响应批量处理**：
- `SyncMessagesResponse` 包含多条消息，必须批量处理
- 使用批量入队接口，避免逐条入队
- 批量写入 ReadStore，减少 I/O 次数
- 批量更新会话，减少数据库操作

**实现思路**：
- MessageQueue 支持批量入队接口
- ReadStore 支持批量写入接口
- 会话更新使用批量 UPSERT

### 8.3 内存优化

**优化策略**：
- 使用引用传递，避免不必要的克隆
- 大 payload 使用零拷贝技术（Arc<[u8]>）
- 及时释放不需要的数据
- 使用对象池复用临时对象

### 8.4 并发优化

**异步流水线**：
- 网络层 → 协议层 → 应用层，各环节异步解耦
- 使用无锁数据结构（DashMap、crossbeam）
- 避免热点锁竞争

**批量并发**：
- 同步响应批量处理，使用并发处理多条消息
- 会话补丁并发处理，提高吞吐

## 9. 错误处理和降级策略

### 9.1 协议降级策略

**设计思路**：支持多级降级，确保向后兼容

**降级流程**：
```
ServerPacket (优先，新协议)
    ↓ 解析失败
MessageEnvelope (向后兼容，旧协议)
    ↓ 解析失败
Message (向后兼容，最旧协议)
    ↓ 解析失败
错误日志 + 转发原始 Frame (由应用层决定)
```

**实现思路**：
- 协议层尝试解析，失败则返回错误
- 应用层根据错误类型决定降级策略
- 记录详细的错误信息，便于排查

### 9.2 错误恢复机制

**设计思路**：
1. **错误隔离**：单条消息处理失败不影响其他消息
2. **自动重试**：可重试的错误自动加入重试队列
3. **错误上报**：不可重试的错误记录日志，上报监控

**实现思路**：
- 使用 Result 类型，明确错误类型
- 区分可重试错误和不可重试错误
- 重试队列支持指数退避
- 错误监控和告警

### 9.3 降级处理

**网络层降级**：
- 解析失败时，转发原始 Frame
- 由应用层决定如何处理
- 不阻塞其他消息的处理

**应用层降级**：
- 消息处理失败时，记录错误但不阻塞
- 同步失败时，记录最后成功位置，支持重试
- 自定义数据处理失败时，记录错误但不影响其他

### 13.3 关键设计决策

#### 决策 1：消息类型为什么转发 Frame 而不是 MessageEnvelope？

**架构师视角分析**：

**原因**：
1. **保持完整性**：Frame 包含 message_id、metadata、reliability 等元数据，这些信息在处理过程中可能需要
2. **避免重复解析**：如果转发 MessageEnvelope，应用层还需要从 Frame 中提取，造成重复解析
3. **统一处理路径**：所有消息都通过同一个解析器（parser.rs），逻辑统一，易于维护
4. **延迟解析**：只在需要时才解析 MessageEnvelope，避免不必要的解析开销

**权衡**：
- ✅ 优点：性能更好（避免重复解析），逻辑统一，易于扩展
- ⚠️ 缺点：需要保留 Frame 引用（使用 Arc），内存占用略高

**参考实践**：
- **微信**：消息处理保持 Frame 完整性，延迟解析 payload
- **Telegram**：使用 Frame 传递，应用层按需解析

#### 决策 2：同步响应为什么转发结构化数据而不是 Frame？

**架构师视角分析**：

**原因**：
1. **批量处理需求**：同步响应包含多条消息/会话，需要批量处理，结构化数据更高效
2. **不需要 Frame 元数据**：同步响应不需要 Frame 的 message_id、metadata 等信息
3. **应用层直接使用**：结构化数据可以直接使用，无需再次解析
4. **性能优化**：避免 Frame → ServerPacket → Response 的多次转换

**权衡**：
- ✅ 优点：应用层处理更简单，性能更好，代码更清晰
- ⚠️ 缺点：丢失了 Frame 的元数据（如果需要，可以在 Response 中扩展）

**参考实践**：
- **微信**：同步响应使用结构化数据，批量处理提高性能
- **Telegram**：同步响应直接传递结构化数据，避免重复解析

#### 决策 3：ACK 为什么不经过路由？

**架构师视角分析**：

**原因**：
1. **网络层机制**：ACK 是网络层的确认机制，由 `send_frame_and_wait` 自动匹配，与应用层业务无关
2. **性能优化**：避免不必要的路由开销，ACK 处理在热路径中
3. **职责清晰**：ACK 处理属于网络层职责，不应进入应用层
4. **简化设计**：减少消息类型，简化路由逻辑

**权衡**：
- ✅ 优点：性能更好，职责清晰，设计更简洁
- ⚠️ 缺点：如果需要应用层处理 ACK（如统计、监控），需要扩展机制

**参考实践**：
- **微信**：ACK 在网络层处理，应用层只关心业务结果
- **Telegram**：ACK 自动匹配，不进入应用层

## 14. 实现架构思路

### 14.1 消息路由实现思路 (`router.rs`)

**架构设计**：
- **无状态设计**：路由器不保存状态，纯函数式，易于测试和并发
- **路由表模式**：使用模式匹配实现路由表，清晰的路由规则
- **降级策略**：未知类型自动降级，转发原始 Frame

**实现策略**：
- 使用 `match` 表达式实现路由表，类型安全
- 支持路由规则扩展，新增类型只需添加一个 match 分支
- 错误处理：路由失败时记录详细日志，转发原始 Frame 由应用层决定

**性能考虑**：
- 路由决策在热路径中，使用早期返回优化
- 避免不必要的克隆，使用引用传递
- 支持路由规则缓存（如果需要）

### 14.2 同步处理器实现思路 (`sync_handler.rs`)

**架构设计**：
- **批量处理优先**：同步响应包含多条消息，必须批量处理
- **游标原子更新**：所有消息处理完成后才更新游标，确保一致性
- **自动分页**：has_more = true 时自动触发下一批同步

**实现策略**：
- **批量解析**：一次性解析 MessageEnvelope 中的所有消息
- **批量入队**：使用批量接口，减少锁竞争和系统调用
- **批量写入**：批量写入 ReadStore，减少 I/O 次数
- **游标管理**：使用事务确保游标更新的原子性

**性能优化**：
- 并发处理多条消息，提高吞吐
- 使用批量接口，减少系统调用
- 内存优化：使用引用传递，避免不必要的克隆

### 14.3 会话同步处理器实现思路 (`conversation_sync_handler.rs`)

**架构设计**：
- **补丁模式**：使用增量补丁而非全量替换，减少数据传输
- **分类处理**：不同 patch_type 使用不同的处理策略
- **补丁合并**：同一会话的多个补丁可以合并处理

**实现策略**：
- **补丁预处理**：按 conversation_id 分组，合并同一会话的补丁
- **分类处理**：
  - LIGHT：只更新关键字段，使用轻量更新
  - SUMMARY：更新完整会话信息，使用全量更新
  - REMOVED：标记为已删除，使用软删除
  - CREATED：创建新会话，触发详情拉取
  - DETAIL_REQUIRED：异步拉取详情，不阻塞同步
- **批量更新**：多个补丁批量更新 ReadStore，减少数据库操作

**性能优化**：
- 补丁合并减少更新次数
- 批量更新减少 I/O 操作
- 详情延迟加载避免阻塞同步流程

### 14.4 自定义数据处理器实现思路 (`custom_data_handler.rs`)

**架构设计**：
- **插件化架构**：支持动态注册和卸载处理器
- **类型路由**：根据 data_type 路由到不同的扩展处理器
- **错误隔离**：单个扩展失败不影响其他扩展

**实现策略**：
- **扩展注册**：通过 ExtensionRegistry 注册自定义处理器
- **类型匹配**：支持精确匹配和通配符匹配（如 "order.*"）
- **处理器链**：支持多个处理器依次处理同一 data_type
- **事件发布**：处理完成后发布自定义事件，UI 层可以订阅

**扩展机制**：
- 支持扩展的初始化和销毁回调
- 支持扩展的配置和状态管理
- 支持扩展的依赖管理

### 14.5 消息处理器的集成思路

**架构设计**：
- **统一入口**：`client.rs` 作为统一的消息接收入口
- **类型分发**：根据 NetworkMessage 类型分发到不同处理器
- **错误处理**：统一的错误处理和日志记录

**实现策略**：
- 在 `client.rs` 的消息接收循环中，根据 NetworkMessage 类型分发
- 使用 `match` 表达式实现类型分发，类型安全
- 每个处理器独立处理，错误隔离

**集成方式**：
- SyncHandler、ConversationSyncHandler、CustomDataHandler 作为独立模块
- 通过依赖注入的方式集成到 SDK 中
- 支持动态启用和禁用处理器

## 15. 关键架构决策总结

### 15.1 为什么需要协议层？

**架构师视角**：

**问题**：为什么不在网络层直接处理所有逻辑？

**答案**：
1. **职责分离**：网络层只负责帧级别的处理，协议层负责协议级别的处理
2. **可测试性**：协议层无状态，易于单元测试
3. **可扩展性**：新增协议类型只需修改协议层，不影响网络层
4. **性能优化**：协议层可以缓存解析结果，避免重复解析

**参考实践**：
- **微信**：网络层和协议层分离，协议层负责协议解析和路由
- **Telegram**：MTProto 层专门负责协议解析，Transport 层负责路由
- **飞书**：协议层统一处理协议解析和分类，业务层只负责处理

### 15.2 为什么消息和同步要分开处理？

**架构师视角**：

**问题**：为什么不能统一处理消息和同步响应？

**答案**：
1. **处理策略不同**：
   - 实时消息：单条处理，实时性优先
   - 同步消息：批量处理，吞吐量优先
2. **性能要求不同**：
   - 实时消息：低延迟，快速响应
   - 同步消息：高吞吐，批量处理
3. **业务语义不同**：
   - 实时消息：用户主动接收，需要实时通知
   - 同步消息：后台同步，不需要实时通知

**参考实践**：
- **微信**：实时消息和同步消息使用不同的处理队列
- **Telegram**：实时消息和同步消息使用不同的处理策略
- **飞书**：实时消息和同步消息完全分离，避免相互影响

### 15.3 为什么 ACK 不在应用层处理？

**架构师视角**：

**问题**：为什么 ACK 不能像其他消息一样进入应用层？

**答案**：
1. **网络层机制**：ACK 是网络层的确认机制，与应用层业务无关
2. **性能考虑**：ACK 处理在热路径中，网络层处理更高效
3. **职责清晰**：ACK 处理属于网络层职责，不应进入应用层
4. **简化设计**：减少消息类型，简化路由逻辑

**权衡**：
- 如果需要应用层处理 ACK（如统计、监控），可以通过回调机制扩展
- 不进入应用层，避免不必要的路由和处理开销

### 15.4 批量处理的架构设计

**架构师视角**：

**为什么需要批量处理？**
- 同步响应包含多条消息（10-100 条），逐条处理效率低
- 批量处理可以减少系统调用、减少锁竞争、提高吞吐

**如何设计批量处理？**
1. **批量接口**：MessageQueue 支持批量入队接口
2. **批量写入**：ReadStore 支持批量写入接口
3. **批量更新**：会话批量更新，减少数据库操作
4. **并发处理**：多条消息并发处理，提高吞吐

**参考实践**：
- **微信**：同步消息批量处理，批量写入数据库
- **Telegram**：批量处理消息，批量更新状态
- **飞书**：批量处理会话补丁，批量更新会话列表

## 16. 架构总结

### 15.1 核心设计理念

**三层架构，职责清晰**：

1. **网络层最小化**：只做必要的过滤和转发，保持纯净
2. **协议层专业化**：专门负责协议解析和路由，无状态设计
3. **应用层业务化**：专门负责业务处理和状态管理，支持扩展

| **自定义推送** | CustomDataHandler | 插件化分发 | 类型路由、扩展机制、事件发布 |
